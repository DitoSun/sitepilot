# SitePilot

**给你的 AI 编程 Agent 补上「生产环境的经验」。**

> 你的 Agent 已经会写代码了。
> SitePilot 教它：代码写完之后，还可能出什么问题。

SitePilot 是一个开源的网站运营 Skill，教 AI 编程 Agent 如何安全地部署、验证、排障和运营真实网站。

**118 条经验 · 20 个负向测试 · MIT 许可**

## 这是什么

SitePilot 补的是 Agent 普遍缺的那部分判断力——代码之外、生产环境之内。

在动手之前，Agent 必须先回答：

- 动手之前我要检查什么？
- 哪些东西我绝对不允许猜？
- 这次改动的风险有多高？
- 什么情况下必须停下来问人？
- 我怎么证明生产环境真的正常？

**核心是技术栈无关的。** 某个栈特有的坑放在 `recipes/` 里，Agent 先识别项目用的是什么，再按需加载。

## 为什么需要它

| 看起来成功了 | 实际证明了什么 |
|---|---|
| 部署成功 | ≠ 线上能用 |
| HTTP 200 | ≠ 业务语义正确 |
| 有备份 | ≠ 备份能恢复 |
| `.gitignore` 里写了规则 | ≠ 敏感文件没被跟踪 |
| 沿用了现有鉴权写法 | ≠ 这套鉴权是安全的 |

这几件事，防起来都很便宜，发现的时候都很贵。

## 快速开始

没有构建步骤，没有依赖——一个 Markdown 文件夹加一个 shell 脚本。

```bash
git clone https://github.com/DitoSun/sitepilot.git
```

然后告诉你的 Agent：

> **读 `sitepilot/SKILL.md`，这个网站按 SitePilot 的规则来。**

安装就这些。`SKILL.md` 会按任务把 Agent 路由到需要的模块，不需要提前读完 references、playbooks 和 docs。

## 真实使用中撞出来的经验

SitePilot 第一次进真实生产环境，确实找到了问题（一张过期的 TLS 证书）——然后顺便发现自己也有问题：它自带的健康检查脚本会在失败的情况下报成功。

我们没有悄悄打补丁了事，而是让这次失败走了一遍 Skill 自己的闭环：

```
事故 → 根因 → 经验 → 泛化 → 修复 → 负向测试 → 更强的 Skill
```

经验库从 111 条涨到 **118** 条，健康检查脚本现在附带 20 个负向用例的回归套件，专门验证「该失败的时候真的会失败」。细节见 [`docs/validation.md`](docs/validation.md)。

## 经验也可能是错的

早期有条经验写着：新增管理接口要沿用生产代码里现有的鉴权写法。

三个接口照做了——后来发现，那套「现有的写法」本身就是漏洞。

所以经验现在带状态：`CHALLENGED`／`CORRECTED`／`SUPERSEDED`／`RETIRED`，纠错时保留历史，不删旧条目。

一条写着「照抄现有实现」的经验，除非它同时写了「先确认现有实现是对的」，否则就是个危险信号。

## 经验构成

同一批知识的两组不同切法。**不要把两组数字相加**，它们不是两个池子。

**按来源**

```
111  来自一个真实生产网站的事故史
  7  来自真实上线测试（dogfooding）
───
118  合计
```

**按证据强度**

```
116  有真实运营证据支撑
  2  明确标注为 GENERAL（通用实践，没有第一手证据）
───
118  合计
```

证据强度在 `references/` 里以 `[REAL]`（真实事故）、`[DERIVED]`（由真实证据推导）、`[GENERAL]`（通用最佳实践）标注在规则层级。经验到执行点的映射表在 [`docs/experience-mapping.md`](docs/experience-mapping.md)；7 条真实使用中得到的经验，各自的来源说明在 [`docs/experience-log.md`](docs/experience-log.md)。

我们追求的是**先深后广**：从一个真正长期运营的站点里持续提炼，而不是把网上的运维 checklist 拼一拼。

## 核心原则

**先检测，再动手。
先备份，再冒险。
部署之后要验证。
事故扩大之前先回滚。
一个坑只踩一次，永久防住。**

## 工作流

SitePilot 给每个任务套一层纪律：

```
理解 → 检查 → 评估风险 → 计划 → 按需备份
→ 最小改动 → 本地验证 → 部署
→ 生产验证 → 观察 → 记录经验
```

外加风险分级模型（LOW → CRITICAL）、明确的**停止条件**，以及一个**自我进化的经验闭环**：每次事故都会沉淀成一条规则、一个检查项、一条排障路径，或一个自动检查。

**SitePilot 会从运营中学习**——是结构化的知识演进，不是模型训练：经验先记在本地，谨慎泛化，只有经明确批准才回馈上游。

## 用法

正常和 Agent 说话就行，SitePilot 会自动路由：

| 你说 | SitePilot 加载 |
|---|---|
| 「部署新版本」 | `checklists/pre-deploy.md` + `references/deployment.md` |
| 「网站打不开了」 | `playbooks/website-down.md`（12 层定位） |
| 「把这些数据改一下」 | `checklists/database-change.md`（先 SELECT 预览） |
| 「我要换域名」 | `checklists/dns-change.md` + 风险确认 |
| 「检查一下 SEO」 | `checklists/seo-change.md` + `references/seo.md` |
| 「网站很慢」 | `playbooks/performance-incident.md` |
| 「API key 泄露了」 | `references/security.md` |

### 一个例子：差别在哪

> **你**：「刚部署完，新接口返回 200，但用户说看不到新内容。」

没有 SitePilot 时，Agent 通常会判断「接口没问题，应该是前端 bug」，然后开始改 UI。

有 SitePilot 时，Agent 会：

1. 意识到 **200 ≠ 正确**（`SKILL.md` §8——静默降级比报错更危险）
2. 检查这个接口的记录数和数据新鲜度 → 发现返回的是被截断或过期的结果集
3. 追到真正的原因（令牌过期 → 走了软降级分支）
4. 修完做语义验证，并在本地记下一条 Lesson Candidate

## 安全设计

SitePilot 是照着生产环境设计的：

- **停止条件**：13 条明确的「必须停下来报告并询问」的情形，而不是硬着头皮上
- **绝不猜基础设施**：先检测 → 再确认 → 才动手
- **可逆优先**：高风险改动前先建并验证回滚点
- **自动化只读**：附带的脚本只发 GET/HEAD 请求和本地 TLS 检查——不写文件、不重启服务、不记录敏感信息
- **连自己都要测**：`bash scripts/tests/health-check-regression.sh` 会验证健康检查在该失败时真的失败。只通过过、没失败过的检查，什么都不能证明
- **只记经验，不记秘密**：凭据、令牌、用户数据和私有基础设施信息绝不进入 Skill 或它的输出
- **证据诚实**：每条规则都标了 `[REAL]`（真实事故）、`[DERIVED]`、`[GENERAL]`（通用实践）——不把通用建议包装成踩过的坑

## 贡献

最有价值的贡献是**你的事故**。SitePilot 的经验库靠一条结构化流程生长：

```
事故 → 证据 → 根因 → 经验 → 泛化
→ 分类 → 隐私审查 → 提交
```

具体模板和审核标准见 [CONTRIBUTING.md](CONTRIBUTING.md)。社区经验只有在描述真实、可复现、且能找到根因的问题时才会被合入——偶发现象不收。

